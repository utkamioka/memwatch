# memwatch — Linux 用メモリリーク監視ツール

自作のサービスやデーモンのメモリ使用量を定期的に記録し、メモリリークが起きているかを判定するツールです。

- **Bash と標準コマンドだけで動作**します。Python などの追加インストールは不要です。
- `collect` は、crontab から定期実行してメモリ情報を CSV に1行ずつ追記します。常駐しないので、screen や tmux がない環境でも、端末を切り離さずに監視を続けられます。
- `graph` は、CSV から増加傾向（MB/時）を計算し、グラフ入りの HTML を出力します。閾値を超えると警告を出します。

## 2. 動作環境

- 対象 OS は RHEL 10 を想定しています。/proc と systemd の cgroup を使うため、RHEL 7 から 10 まで動く設計です。
- 使用するコマンドは次のとおりです。いずれも最小構成に含まれています。
  - `bash awk sort date flock find grep sed ps pgrep systemctl logger`
- awk は gawk と mawk のどちらでも同じ結果になります。そのため `graph` は Windows の Git Bash や WSL でも実行できます。

### 設計の背景（なぜ Bash と cron なのか）

このツールは、**サブスクリプション未登録の RHEL** で使うことを前提に設計しています。こうした環境では dnf でパッケージを追加できないことが多く、pip も入っていません。そのため、次の2つの方針をとっています。

**Bash と標準コマンドだけで作る理由**

Python の matplotlib のような外部ライブラリは導入できません。そのため、OS に最初から入っているコマンドだけで作っています。グラフも、画像ライブラリを使わずに awk で SVG を組み立て、HTML に埋め込む方式にしています。

**常駐させず、cron で定期実行する理由**

- 監視を長時間続けるには、通常は screen や tmux を使ってプログラムを端末から切り離し、バックグラウンドで動かします。しかし上記の環境ではこれらを導入できず、SSH を切断すると、前面で動かしていたプログラムも止まってしまいます。
- `nohup` や `setsid` を使えば端末から切り離すことはできます。ただし次の問題があります。
  - OS を再起動すると監視が止まり、手動で起動し直す必要がある。
  - 停止や状態確認のために、PID を探す手間がかかる。
  - 監視プロセスが異常終了しても気づきにくい。
- cron は OS 標準のサービス（crond）として常に動いているので、端末とは関係なく定期実行できます。この方式には次の利点があります。
  - 端末を切り離す操作が要らない。SSH を切断しても監視が続く。
  - OS を再起動しても自動で再開する。
  - 1回ごとに起動して終了するので、仮に1回失敗しても次の回は通常どおり動く。
  - 監視ツール自体が常駐しないので、**監視ツールのメモリ使用量が増えていく心配がない**。

cron が動いているかは、`systemctl is-active crond` で確認できます。

## 3. 導入

```bash
sudo mkdir -p /root/memwatch /var/log/memwatch
sudo cp memwatch.sh /root/memwatch/
sudo chmod +x /root/memwatch/memwatch.sh
sudo sed -i 's/\r$//' /root/memwatch/memwatch.sh   # Windows 経由で転送した場合の CRLF 対策

# 動作確認
sudo /root/memwatch/memwatch.sh collect --service myapp -v

# cron 登録（中身の myapp や実行ユーザーを環境に合わせて書き換えること）
sudo cp memwatch.cron /etc/cron.d/memwatch
```

### 実行ユーザー

本体は root のホームディレクトリ（`/root/memwatch`）に置く前提です。`/root` には root 以外は入れないため、**cron は root で実行します**（`memwatch.cron` の設定例も root で書いてあります）。root で実行すれば、他ユーザーのプロセスについても PSS と FD 数を含めてすべての項目が取れます。

実行するユーザーによって、取れる項目は次のように変わります（参考）。

| 項目 | 一般ユーザー | アプリと同じユーザー | root |
|---|---|---|---|
| システムのメモリ、RSS、RssAnon、Swap、スレッド数 | 取れる | 取れる | 取れる |
| PSS、FD 数 | 取れない（空欄） | 取れる | 取れる |

将来、root 以外のユーザー（たとえばアプリと同じユーザー）で動かしたくなった場合は、本体を `/usr/local/bin` のような誰でも読める場所に移し、`/var/log/memwatch` の所有者をそのユーザーに変更する必要があります。

## 4. 使い方

### collect（記録）

```
memwatch.sh collect [対象] [--csv PATH] [-v]
```

対象は次のいずれか1つを指定します。

| オプション | 対象 |
|---|---|
| `--service NAME` | systemd サービスの cgroup に属する**全プロセスの合計**（名前の違う子プロセスも含む） |
| `--name NAME` | プロセス名（comm）が完全一致するプロセスの合計 |
| `--cmdline TEXT` | コマンドラインに TEXT を含むプロセスの合計（memwatch 自身は除外） |
| `--pidfile PATH` | PID ファイルに書かれたプロセス |
| `--pid PID` | 指定した PID |
| 指定なし | システム全体のメモリだけを記録 |

その他のオプションは次のとおりです。

- `--csv PATH`：出力先を指定します（既定は `/var/log/memwatch/memwatch.csv`）。`date` の書式が使えるので、`/var/log/memwatch/app_%Y%m%d.csv` のようにすると日付ごとにファイルを分けられます。
- `-v`：結果を1行で表示します。

### graph（分析とグラフ出力）

```
memwatch.sh graph [--csv FILE...] [-o OUT.html] [--hours N]
                  [--warn-mb-per-hour N] [--min-hours N] [--min-r2 N]
```

| オプション | 意味 | 既定値 |
|---|---|---|
| `--csv FILE...` | 入力する CSV。複数指定やワイルドカードも可 | `/var/log/memwatch/memwatch.csv` |
| `-o OUT.html` | 出力する HTML。`""` を指定すると HTML は出さずサマリーだけ表示 | `/var/log/memwatch/memwatch.html` |
| `--hours N` | 直近 N 時間分だけを対象にする | 全期間 |
| `--warn-mb-per-hour N` | RSS の増加率が N MB/時を超えたら警告する | 判定しない |
| `--min-hours N` | 警告を出すのに必要な最低観測時間 | 2 |
| `--min-r2 N` | 警告を出すのに必要な R²（直線的に増えているかの指標） | 0.6 |

実行すると、次のようなサマリーが出力されます。

```
対象: myapp  期間: 2026-09-27 09:06:40 ～ 2026-09-28 21:01:40 (432 サンプル)
再起動検出: 1 回 / 傾向計算区間: 直近 19.2 時間
  RSS              +2.072 MB/時  (   +49.7 MB/日, R^2=1.00)
  PSS              +2.072 MB/時  (   +49.7 MB/日, R^2=1.00)
  MemAvailable     -4.143 MB/時  (   -99.4 MB/日, R^2=1.00)
グラフ出力: /var/log/memwatch/myapp.html
```

終了コードは次のとおりです。

| 終了コード | 意味 |
|---|---|
| 0 | 正常終了 |
| 1 | エラー、またはデータ不足（2行未満） |
| 2 | リークの疑いがある |

終了コード2のときは、stderr に `WARNING:` を出力し、syslog にも記録します（`logger -t memwatch -p user.warning`）。cron で実行していれば、MAILTO に設定した宛先へメールが届きます。syslog は `journalctl -t memwatch` で確認できます。

## 5. メモリリーク計測の仕組み

### 5.1 基本の考え方

メモリリークとは、「確保したメモリが解放されず、**稼働時間に比例して使用量が増え続ける**」状態です。一時的に大きく使うだけ（キャッシュやプールの確保）ならリークではありません。

そこで、**一定間隔でメモリ使用量を記録し、時間に対する増加の傾きと、その増え方の一貫性を統計的に見る**ことで判定しています。

### 5.2 何を記録しているか（collect）

1分ごとなど決まった間隔で、次の情報を読み取り、CSV に1行追記します。

**システム全体の値（`/proc/meminfo`）**

- **MemAvailable** を主な指標にしています。MemFree はページキャッシュに使われるだけでも減っていくため、リークがなくても減少して見えます。MemAvailable は、カーネルが「キャッシュを解放すれば使える量」まで含めて見積もった値なので、実際に使える空き容量に近い値になります。
- MemFree、Buffers、Cached、SwapTotal、SwapFree も参考値として記録しています。

**対象プロセスの値（`/proc/PID/...`）**

| 指標 | 読み取り元 | 意味 |
|---|---|---|
| RSS（VmRSS） | status | 物理メモリ上にある量。**リーク判定の基準にする値** |
| RssAnon | status | ファイルに対応しない匿名メモリ（ヒープや mmap の匿名領域など）。**malloc/new のリークはここに現れる** |
| PSS | smaps_rollup | 共有ページをプロセス数で按分した量。子プロセスを合計するときに二重計上しない |
| VmSize | status | 仮想メモリのサイズ（参考値） |
| VmSwap | status | スワップアウトされた量。RSS が増えずに Swap だけ増えるリークを見逃さないため |
| Threads | status | スレッド数。スレッドリークの検出に使う |
| FD 数 | fd/ ディレクトリのエントリ数 | ファイル記述子リークの検出に使う |

**対象プロセスの特定方法**

- `--service` では、`systemctl show -p ControlGroup` で cgroup のパスを取得し、配下の `cgroup.procs` を子 cgroup まで含めてすべて読みます。プロセス名に関係なく、サービスから生まれたプロセス（fork やデーモン化したものも含む）がすべて対象になります。cgroup v2、v1、hybrid のどれにも対応しています。
- 複数のプロセスが対象になった場合は、それぞれの値を**合計**します。
- メイン PID は次の方法で決めます。`--service` なら `MainPID` を使い、`--name` と `--cmdline` なら起動が最も古いプロセスを使います。再起動の判定には、このメイン PID を使います。
- 対象が見つからないときは `status=NOT_FOUND` として記録します。プロセスの停止も記録として残ります。

**CSV への書き込み**

`flock` で排他ロックをかけてから追記するので、cron の実行が重なっても行が混ざりません。ファイルが空のときだけヘッダー行を書きます。

### 5.3 どう判定しているか（graph）

1. **再起動の検出**：`main_pid` が変わった位置を再起動とみなします。再起動するとメモリ使用量が初期値に戻るため、再起動の前後をまたいで傾きを計算すると結果が歪みます。そこで**最後の再起動以降の区間だけ**を分析対象にします。
2. **最小二乗法による傾き**：横軸を「区間の開始からの経過時間（時）」、縦軸を「RSS（MB）」として回帰直線を求め、その傾きを **MB/時** として表示します。PSS と MemAvailable も同じ方法で計算します。
3. **決定係数 R²**：回帰直線がデータにどれだけ当てはまっているかを示す値で、0から1の範囲をとります。
   - 1に近いほど、「一定のペースで増え続けている」ことを意味し、リークの典型的な形です。
   - 小さいほど、増減をくり返しているだけで、たまたま傾きが出ている可能性が高くなります。
4. **警告の条件**：次の3つを**すべて**満たしたときに警告します。
   - 観測時間が `--min-hours` 以上（起動直後の確保による増加で誤検知しないため）
   - R² が `--min-r2` 以上（直線的に増えていること）
   - 傾きが `--warn-mb-per-hour` を超えていること

### 5.4 メモリ指標の意味

#### RSS（Resident Set Size：常駐メモリ量）

プロセスが**今この瞬間、物理メモリ（RAM）上に載せている量**です。`top` の RES 列や `ps` の RSS 列と同じ値です。

- 含まれるもの：そのプロセス専用の領域（ヒープやスタックなど）と、ほかのプロセスと共有している領域（libc などの共有ライブラリ、共有メモリ、fork した親子で共有しているページ）
- 含まれないもの：スワップアウトされた分や、確保しただけでまだ一度も使っていない領域

**注意点が2つあります。**

- **共有部分を丸ごと数える**：共有ライブラリはプロセスごとに全量が加算されます。そのため、複数プロセスの RSS を合計すると、共有部分が二重、三重に数えられて実際より大きくなります。
- **新しいカーネルでは概算値になる**：`/proc/PID/status` の VmRSS は、性能を優先して CPU ごとのカウンタを概算で合計した値です。コア数が多いサーバーでは誤差が出て、値がノイズのように上下することがあります。

RSS は次の3つに分けられます。memwatch では、このうち RssAnon も記録しています。

| 内訳 | 中身 | リークとの関係 |
|---|---|---|
| **RssAnon** | ファイルに対応しないメモリ（malloc や new で確保したヒープ、スタック、匿名 mmap） | **malloc/new のリークはここが増える** |
| RssFile | 実行ファイル、共有ライブラリ、mmap したファイル | ファイルの mmap を解放し忘れると増える |
| RssShmem | 共有メモリ（tmpfs、SysV 共有メモリなど） | 共有メモリの解放漏れで増える |

#### PSS（Proportional Set Size：按分した常駐メモリ量）

RSS のうち、**共有している部分を、共有しているプロセスの数で割って按分した値**です。

例として、あるプロセスが専用に 60MB を使い、ほかの3プロセスと共有しているライブラリが 40MB ある場合を考えます（合計4プロセスで共有）。

- RSS は 60 + 40 = **100MB** になります。
- PSS は 60 + 40 ÷ 4 = **70MB** になります。

**全プロセスの PSS を合計すると、実際に使われている物理メモリの量とほぼ一致します。** そのため、子プロセスを持つサービスの合計値を見るときは、RSS より PSS のほうが正確です。

- 取得元は `/proc/PID/smaps_rollup` です。カーネルがページを1つずつ数えて集計するので、正確な値が得られます。
- 読み取るには、そのプロセスと同じユーザーか root である必要があります。
- 1つのプロセスについて見れば、**PSS は必ず RSS 以下**になります。

#### MemAvailable（システム全体の利用可能メモリ）

**スワップを使わずに、新しく起動するアプリにあとどれだけメモリを渡せるか**を、カーネルが見積もった値です。`free` コマンドの available 列と同じ値です。

- 計算の内容は「完全に空いているメモリ（MemFree）＋すぐに解放できるページキャッシュ＋回収できるカーネルのキャッシュ（Slab の一部）」です。
- Linux は空いているメモリを積極的にファイルキャッシュとして使います。そのため MemFree は、長く動いているサーバーほど小さくなっていきますが、これは正常な動きです。**「メモリが足りなくなってきたか」の判断には MemAvailable を使います。**
- MemAvailable が下がり続けている場合は、サーバーのどこかでメモリが消費され続けています。対象プロセスのグラフと見比べることで、そのプロセスが原因なのか、ほかに原因があるのかを切り分けられます。

#### 指標の使い分け

| 知りたいこと | 見る指標 |
|---|---|
| サーバー全体でメモリが減り続けていないか | MemAvailable |
| 対象サービスが実際に使っている量 | PSS（子プロセスがあるときは特に） |
| リークの種類（ヒープかそれ以外か） | RssAnon と RSS を見比べる |
| `top` や `ps` の表示値と照らし合わせる | RSS |

### 5.5 グラフの読み方

#### (1) サマリー（ページ上部の灰色の枠）

```
RSS    +2.072 MB/時  (   +49.7 MB/日, R^2=1.00)
```

| 項目 | 意味 |
|---|---|
| MB/時、MB/日 | 回帰直線の傾き、つまり平均的な増加ペースです。プラスなら増加、マイナスなら減少を表します |
| R² | 増減がどれだけ一定のペースで続いているかを示す値で、0から1の範囲です。1に近いほど「ずっと同じペースで増え続けている」ことを表します |
| 再起動検出 | 期間中に対象プロセスが再起動した回数です。傾きは最後の再起動以降の区間だけで計算しています |

**リークを疑う目安は「傾きがプラス、かつ R² が 0.6 以上」**です。傾きが大きくても R² が小さい場合は、たまたま上下しているだけの可能性が高いと判断できます。MemAvailable はリークがあると減るので、**傾きがマイナス、かつ R² が高い**ときに注意します。

#### (2) 各グラフの見方

| グラフ | 正常なときの形 | リークが疑われる形 |
|---|---|---|
| System memory | MemAvailable が横ばい、または上下を繰り返す | MemAvailable が右肩下がりになる |
| Target process memory | RSS、PSS、RssAnon が一定の範囲で上下する | 右肩上がりになる。または、上下しながら底の値が少しずつ上がっていく |
| Processes / Threads | ほぼ一定。負荷に応じて増減した後、元に戻る | スレッド数が増え続ける（スレッドの終了漏れ） |
| Open file descriptors | 一定の範囲で上下し、下限が変わらない | 下限が少しずつ上がっていく（ファイルやソケットの close 漏れ） |

グラフ中の記号の意味は次のとおりです。

- 赤い点線：再起動した位置
- 赤い網掛け：対象プロセスが見つからなかった区間（停止していた期間）
- 黒い破線：最新区間の RSS の回帰直線

#### (3) パターン別の判断

- **起動直後だけ増えて、その後は横ばい**になっていれば正常です（初期化やキャッシュの確保による増加）。数時間から数日分のデータで判断してください。
- **のこぎり状に上下しながら、底の値も上がっていく**場合は、GC（ガベージコレクション）やメモリプールの動きに隠れたリークの可能性があります。子プロセスを都度生成するサービスでもこの形になります。
- **RssAnon が増えている**場合は、ヒープのリーク（malloc と free、new と delete の対応漏れ、要素が増え続けるキャッシュやリストなど）が疑われます。
- **RSS は増えているのに RssAnon は横ばい**の場合は、ファイルの mmap や共有メモリが原因の可能性があります。
- **RSS は増えているのに PSS は横ばい**の場合は、共有ページが増えているか、RSS の概算誤差によるものです。実際にリークしている可能性は低いと考えられます。
- **MemAvailable は減っているのに対象プロセスは横ばい**の場合は、別のプロセスやカーネル側（Slab など）が原因です。このツールの対象外なので、`/proc/meminfo` の Slab や SUnreclaim、`slabtop` で調べてください。
- **定期的に段差状に増える**場合は、バッチ処理や定期ジョブのタイミングで解放漏れが起きている可能性があります。増えた時刻と、アプリのログを突き合わせてください。

#### (4) PSS が RSS より大きく表示される場合

1つのプロセスで見れば PSS は RSS 以下になるはずですが、グラフでは逆転することがあります。原因は、RSS（`/proc/PID/status` の VmRSS）の概算誤差です。特に RHEL 10 のような新しいカーネルで、コア数が多いサーバーでは誤差が大きくなります。RSS がノイズのように細かく上下し、PSS は安定している場合は、この誤差が原因です。

正確な値は次のコマンドで確認できます。

```bash
pid=$(systemctl show -p MainPID --value myapp)
grep VmRSS /proc/$pid/status                      # 概算の値
grep -E '^(Rss|Pss):' /proc/$pid/smaps_rollup     # 正確な値
```

2つの値が大きく違う場合は、**PSS を主な判断材料にしてください。** 現在の警告判定は RSS の傾きで行っています。

#### (5) 読み方の例

実際の環境（ism-agent.service、4プロセス、約8.5時間分）での読み方の例です。

- **サマリー**：RSS は -1.4 MB/時（R² 0.25）、PSS は +0.1 MB/時（R² 0.01）、MemAvailable は +1.2 MB/時（R² 0.05）でした。どれも R² がほぼ0なので、一方向に増え続けてはいません。
- **System memory**：MemAvailable は約59.7GB で横ばいでした。
- **Target process memory**：RSS は 140〜170MB、RssAnon は 90〜125MB の範囲で上下していて、右肩上がりではありません。PSS（約200MB）が RSS を上回っていたのは、(4) の概算誤差によるものです。
- **Threads と FDs**：スレッド数は約188で一定でした。FD 数は40〜60で上下していましたが、下限の約40は変わっていません。
- **結論**：この期間にリークの兆候はありません。ただし期間が短いので、数日から1週間分のデータで改めて確認するのが確実です。

### 5.6 グラフの生成方法

グラフ描画用のライブラリは使っていません。awk で SVG 要素（`<polyline>`、`<line>`、`<text>`）を組み立て、HTML に埋め込んで出力しています。そのため、ブラウザで開くだけで表示できます。日本語はブラウザのフォントで表示されるので文字化けしません。

## 6. CSV の仕様

- 1行が1回の計測です。区切りはカンマで、ヘッダー行があります。改行コードは LF です。
- 値がない項目は空欄です（未検出、権限不足、非対応カーネルなど）。
- 単位は kB です（`/proc` の値をそのまま記録しています）。

| # | 列名 | 内容 |
|---|---|---|
| 1 | timestamp | 計測時刻（`YYYY-MM-DD HH:MM:SS`、ローカルタイム） |
| 2 | epoch | 計測時刻（UNIX 時間）。並べ替えと計算にはこちらを使う |
| 3 | mem_total_kb | MemTotal |
| 4 | mem_free_kb | MemFree |
| 5 | mem_available_kb | MemAvailable |
| 6 | buffers_kb | Buffers |
| 7 | cached_kb | Cached |
| 8 | swap_total_kb | SwapTotal |
| 9 | swap_free_kb | SwapFree |
| 10 | target | 監視対象の名前（指定した値。カンマは `_` に置き換え） |
| 11 | status | `OK`、`NOT_FOUND`、`SYSTEM_ONLY` のいずれか |
| 12 | main_pid | メイン PID（再起動の判定に使う） |
| 13 | pids | 対象になった PID の一覧（`;` 区切り） |
| 14 | nproc | 対象プロセスの数 |
| 15 | rss_kb | VmRSS の合計 |
| 16 | pss_kb | PSS の合計（1つでも読めないプロセスがあれば空欄） |
| 17 | rss_anon_kb | RssAnon の合計 |
| 18 | vmsize_kb | VmSize の合計 |
| 19 | vmswap_kb | VmSwap の合計 |
| 20 | threads | スレッド数の合計 |
| 21 | fds | FD 数の合計（1つでも読めないプロセスがあれば空欄） |

Excel でグラフにするなら、`timestamp` を横軸にして、`rss_kb` や `mem_available_kb` を折れ線グラフにするのが手軽です。

## 7. 運用上の注意

- **データ量**：1分間隔で1日あたり約1,440行、約200KBになります。日付ごとに CSV を分割し、古いファイルは `find /var/log/memwatch -name '*.csv' -mtime +30 -delete` などで削除してください。
- **graph の対象期間**：cron では `--hours` で期間を絞ってください。数か月分をまとめて処理すると時間がかかります。
- **子プロセスがあるサービス**：RSS の合計は共有ページを二重に数えるため、実際より大きく見えます。PSS を主な判断材料にしてください。
- **起動直後の増加**：初期化による増加は正常な動作です。判定は数時間以上のデータがたまってから行ってください。
- **/proc の hidepid**：`/proc` が `hidepid` オプション付きでマウントされていると、一般ユーザーからは他ユーザーのプロセスが見えません。RHEL の既定ではこのオプションは付いていません。

## 8. 開発者・AI 向けメモ（エンハンス時にこの節を読むこと）

> 機能を追加するときは、**この README.md と memwatch.sh の両方**を AI に渡してください。
> 依頼の例：「README の『開発者・AI 向けメモ』の制約を守って、○○の機能を memwatch.sh に追加して。README も更新して。」

### 8.1 守るべき設計上の制約

1. **Bash と標準コマンドだけで作る**こと。Python、Perl、jq、gnuplot などは使わない。対象の環境は、サブスクリプション未登録で dnf も pip も使えない RHEL 10 である。
2. **awk は gawk と mawk の両方で動くように書く**こと。
   - gawk だけの機能（`strftime`、`asort`、`gensub`、`length(配列)`、`BEGINFILE` など）は使わない。時刻の表示には CSV の `timestamp` 列の文字列を `substr` で切り出して使っている。
   - awk の組み込み変数と同じ名前を変数や配列に使わない（`RS`、`NR`、`FS`、`NF` など）。過去に配列名を `RS` にして mawk で構文エラーになったため、現在は `RSI` と `NR_` を使っている。
   - フィールドの参照は `$(col["name"])` のように括弧で囲む（mawk 対策）。
3. **CSV の互換性を保つ**こと。
   - 既存の列の順番や意味を変えない。**新しい列は必ず末尾に追加する**。graph はスクリプト内の `HEADER` 定数を列の対応表として使い、各 CSV のヘッダー行は読み飛ばしている。末尾に追加した列なら、古い CSV では単に空欄として扱われる。
   - CSV の形式は、以前の Python 版（memwatch.py）と共通である。
4. **collect は軽く保つ**こと。cron で毎分実行されるため、外部コマンドの起動回数を増やしすぎない（今はプロセス1つあたり awk を2回起動し、ls を1回実行している）。
5. **root がなくても動くようにする**こと。読めない値は空欄として記録し、エラーで止めない。
6. **LC_ALL=C を固定する**こと。小数点の表記とソート順を一定にするため。
7. **RHEL 7 の systemd 219 でも動くようにする**こと。`systemctl show --value` は使わず、`-p Prop` の出力を sed で取り出す。
8. **常駐型（ループで sleep し続ける形）にしない**こと。cron から1回ずつ起動して終了する形を守る。screen や tmux、`nohup` を前提にした設計にもしない。理由は 2章の「設計の背景」を参照。

### 8.2 コードの構成（memwatch.sh）

**Bash 部分**

| 関数 | 役割 |
|---|---|
| `die` | エラーを表示して終了する |
| `sysprop UNIT PROP` | systemctl show の値を取得する |
| `find_service` / `find_name` / `find_cmdline` / `find_pidfile` / `find_pid` | 対象プロセスを探し、グローバル変数 `PIDS`（空白区切り）と `MAIN_PID` を設定する |
| `oldest_pid` | 起動が最も古い PID を返す（`ps --sort=start_time` を使用） |
| `collect` | 引数の解析、/proc の読み取り、合計の計算、flock を使った CSV への追記 |
| `graph` | 引数の解析、CSV の結合とソート（`sort -t, -k2,2n`）、awk の呼び出し、HTML の配置、警告の処理 |
| 末尾の `case` | サブコマンドの振り分け。引数がなければ先頭のコメントをヘルプとして表示する |

**awk 部分**（変数 `AWK_GRAPH` にヒアドキュメントで格納）

| 要素 | 役割 |
|---|---|
| メインのルール | ヘッダー行から列の対応表 `col[]` を作り、データ行を配列に格納する |
| `E[i]` `TS[i]` `TG[i]` `ST[i]` `MP[i]` `NP[i]` | 行ごとの epoch、timestamp、target、status、main_pid、nproc |
| `V[key, i]` | グラフ用の値（MB または個数）。値がなければ要素自体を作らない。key は `avail free swapu rss pss anon vmswap nproc thr fds` |
| `END` | `--hours` による絞り込み（`s0`）、再起動の検出（`RSI[]`、`NR_`、`seg`）、回帰計算、サマリーの出力、警告の判定、HTML の出力 |
| `linreg(key)` | 区間 `seg..n` について最小二乗法を計算し、`LS[key]`（傾き、MB/時）、`LB[key]`（切片）、`LR2[key]`（R²）を設定する |
| `chart(title, ylabel, h, spec, trend, spans)` | SVG のグラフを1枚生成する。spec は `"key\|ラベル\|色[\|nz]"` を `;` でつないだもので、`nz` を付けるとすべて0の系列は表示しない |
| `niceticks` `fmtn` `X` `Y` `legend` `poly` `esc` `floor_` | 目盛りの計算、数値の整形、座標変換、SVG 部品の生成、HTML エスケープ |

**awk と bash のやりとり**

- awk の標準出力にはサマリーを出力します。警告があるときは、`@@WARN@@ <メッセージ>` という行を追加で出力します。bash 側はこの行を取り除いて画面に表示し、代わりに logger での記録と終了コード2の返却を行います。
- HTML は `OUT` に一時ファイル（`出力先.tmp`）として書き、bash 側が `mv` で置き換えます。書き込みの途中でファイルを開かれても、壊れた HTML が見えないようにするためです。

### 8.3 テスト方法

**意図的にリークさせるプロセスを使う**

```bash
cat > /tmp/leakyapp <<'EOF'
#!/bin/bash
# 1秒ごとに約1MBずつメモリが増えていく
a=""; while :; do a+=$(head -c 1000000 /dev/zero | tr '\0' x); sleep 1; done
EOF
chmod +x /tmp/leakyapp; /tmp/leakyapp & P=$!
for i in $(seq 10); do ./memwatch.sh collect --cmdline leakyapp --csv /tmp/t.csv -v; sleep 1; done
kill $P; ./memwatch.sh collect --cmdline leakyapp --csv /tmp/t.csv -v   # NOT_FOUND
./memwatch.sh graph --csv /tmp/t.csv -o /tmp/t.html --warn-mb-per-hour 1 --min-hours 0; echo rc=$?
```

**確認するポイント**

- `bash -n memwatch.sh` で構文エラーがないこと。
- gawk と mawk の両方で `graph` を実行し、出力が同じになること（生成日時の行は除く）。
- `status` が OK、NOT_FOUND、SYSTEM_ONLY のどの行でも列数が21であること。
- 再起動（main_pid の変化）の後から傾きが計算されていること。
- 一般ユーザーで実行したときに、PSS と FD 数が空欄になり、エラーで止まらないこと。

**確認済みの環境とまだ確認していないこと**

- 確認済み：Ubuntu 上の bash、mawk、gawk で、`--cmdline`、`--name`、`--pidfile`、`--pid`、system のみ、graph を実行。
- **まだ実機で確認していない**：RHEL 10 の実機での `--service`（systemd の cgroup を読む部分）。導入時に `collect --service NAME -v` の結果と、`systemd-cgls -u NAME.service` の出力が一致するか確認すること。
